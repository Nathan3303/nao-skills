# 普通用户文案写作规范

## 目标

约束两件事：**怎么用中文写**，**怎么用 Markdown**。

章节怎么组织、分几节、先写什么后写什么，由内容决定，本 skill 不作规定。但每一句话的措辞、每一个 Markdown 元素的使用，都必须符合下面的规则。

读者是不懂技术的普通用户。判断标准只有一条：**他能不能照着做出来。**

## 适用场景

- 产品功能的使用说明、上手教程
- 按用户任务组织的操作指南
- 设置与偏好说明
- 常见问题与自助排查
- 把技术文档改写成普通用户能读的版本

## 输入检查

优先读取：产品说明、已有帮助文档、界面文案、功能清单、客服问答、用户反馈。

信息不足时：

- 最多问 3 个影响操作正确性的问题
- 其余用 `TODO(确认): ...` 标记
- 不编造按钮名、菜单路径、页面提示语

## 一、写作文法

### 1. 人称与语气

- 用「你」称呼读者，不用「用户」「操作者」「使用者」。
- 用陈述句和祈使句，不用反问句、设问句。
- 语气平实，像同事在旁边教你，不像客服话术，也不像广告。
- 不堆敬语：「请您」「烦请」「敬请」一律不用。

### 2. 句子

- 一句话只表达一个意思（**原则，不许删**）。
- **出现下列情况就拆**：单句超过 70 字；或一句里塞了 3 个及以上动作（例：「去掉这一条，删掉那个脚本，再清理设置里的引用」）。
- 不要拿字数当尺子只看长度：「一句三动作但只有 60 字」同样要拆，「80 字但只有一个意思」可不拆。
- 主语尽量是「你」或具体的东西，少用无主句堆叠。
- 先说要做什么，再说为什么；原因不重要时直接省掉。
- 不用长定语。「点击位于页面右上角的那个带有齿轮图标的设置按钮」应写成「点击页面右上角的「设置」」。

### 3. 动词优先

- 用具体动词：点击、输入、选择、拖动、粘贴、保存、刷新。
- 不用抽象动词：进行操作、执行、完成、实现、处理、配置。
- 「进行设置」写成「设置」；「完成保存操作」写成「保存」。

### 4. 术语处理

- 能换成日常词就换：部署 → 上线/发布，配置 → 设置。
- 必须保留的专业词，第一次出现时用一句话解释，之后直接使用。
- 同一个东西全文只用一个叫法，不换同义词。
- **已弃用的东西不删，保留一句「是什么 + 现在怎么办」**：升级过来的读者可能在旧配置、旧文档、旧命令里仍见到它（例：某个旧参数、旧标记文件）。整条删掉等于让人搜不到解释。
- 术语名不要整名加粗；定义句拆成「是什么」和「什么时候用」两段。
- 界面上的文字（按钮、菜单、选项）用「」括起来，且与界面完全一致，不近义改写。

### 5. 提示与反馈

- 每个关键操作后面告诉读者会看到什么：「你会看到页面顶部出现绿色提示」。
- 结果用看得见的现象描述，不用「操作成功」这类空话。
- 有风险的操作，把后果写在动作前面，不写在后面。

### 6. 禁止的表达

- 营销词：强大、高效、一站式、致力于、极致、无缝、赋能
- 套话开头：本文档介绍了、下面我们来了解一下、众所周知
- 技术黑话：接口、参数、配置项、字段、部署、实例、端点、环境变量、回调
- 模糊指代：相关设置、相应选项、上述功能、某些情况下
- 双重否定和被动堆叠：「若未被勾选则不可被提交」

## 二、Markdown 元素运用

总原则：**元素服务于可读性，不做装饰。** 一个元素如果删掉之后读者照样能看懂，就不要用。

### 1. 标题

- 标题写用户会说的话，不写功能模块名。「如何导出报表」优于「报表导出模块」。
- 标题里不加句号，不加序号（不写「一、」「1.」），层级本身已经表达顺序。
- 层级不跳级，不为了字号好看而用错层级。
- 标题下紧跟正文，不出现空标题。

### 2. 列表

- **有序列表**用于有先后顺序的操作步骤，一步一项。
- **无序列表**用于并列的清单、条件、注意事项，顺序无所谓时用。
- 一项只写一件事，不在一项里塞两个动作。
- 列表项是完整句子时加句号，是短语时统一不加，全文保持一致。
- 嵌套不超过两层，第二层只用于补充说明上一步。
- 不用列表写连续段落，那应该写成正文。

### 3. 表格

- 只在**多行多列存在对应关系**时使用，比如「问题 → 原因 → 做法」「设置项 → 效果」。
- 两列且内容很短时，考虑改成列表或正文，表格不是默认选择。
- 表头用用户能懂的话，不用「参数」「字段名」「类型」。
- 单元格内不塞长段落，超过两行说明该换正文。

### 4. 加粗与斜体

- 加粗只用于两类：**关键动作**和**会出错的地方**。
- 一段里加粗不超过两处。通篇加粗等于没加粗。
- **判例（允许/违规）**：并列的列表项各自一个加粗 = 允许（例：七个页面各三条「易错点」标签）；同一段落或同一项内 ≥3 处 = 违规；术语名整名加粗 = 违规。
- **语义判据（比数数量更好用）**：读完这句，读者会不会因此**避免一次返工或事故**？会 ⇒ 允许；只是「看起来重要」⇒ 违规。
- 斜体在中文里可读性差，基本不用，强调一律用加粗。

### 5. 行内代码与代码块

- 面向普通用户的文案，**默认不用**代码块和行内代码。
- 唯一例外：用户需要**原样复制一段内容**（如邀请码格式、一段要粘贴的文本）时，用行内代码包裹，并说明「原样复制」。
- 不把按钮名、菜单名写成行内代码，用「」。
- 不展示命令行、配置文件、JSON、环境变量。

### 6. 引用块与提示块

- 引用块用于**需要单独拎出来的提醒**：会导致数据丢失的操作、容易忽略的前提。
- 提醒控制在两句以内，长了就改成正文。
- GitHub 风格提示块（`> [!NOTE]`、`> [!WARNING]`）**仅在确认目标渲染环境支持时使用**，否则退回普通引用块。
- 一段文案里提示块不超过两个，否则提醒失去分量。

### 7. 链接与图片

- 链接文字要说明点进去是什么，不写「点击这里」「详见此处」。
- 图片只在**界面无法用文字说清**时使用，配一句图注说明看什么。
- 图片不替代步骤文字，读者可能加载不出图。

### 8. 分隔线与折叠块

- 分隔线只在两个明显无关的大板块之间使用，正文中不用来分隔小节。
- 折叠块（`<details>`）只在内容确实是可选补充（如进阶说明、历史版本差异）时使用，不能把必读步骤折叠起来。

### 9. 通用约束

- 一段不超过 4 行，超过就拆段或改列表。
- 不用 emoji 做装饰性标记。
- 不混用中英文标点，中文文案统一用中文标点。
- 数字、单位、界面文字之间保持一致的空格习惯。

### 10. 终端示意与输出模拟

- **示意只描述紧邻那条命令的后果**；多步后果必须分开写，禁止合并（例：体检命令后面不要写「你会看到 N 个窗口亮起」——体检不拉会话）。
- **三种载体都算**：代码围栏块、YAML/JSON 字段渲染（如 `kind: cmd` / `text:`）、带 `←` 注释的输出、截图式模拟。条款不因载体不同而失效。
- 示意里的数字必须与紧邻命令的真实结果一致；会在不同机器/版本变化的数字（文件数、例数、行数）要标注「随版本变，对不上不算坏」并给出真正的判据。

### 11. 同一内容出现在多处

- 同一段说明出现在两个页面（如首页摘要与常见问题）时，视为**单一来源**：改动必须全量同步。
- 更优先的做法是**引用而非复制**——能链接到一处就别复制第二份。
- 无法避免复制时，改完必须逐字比对（只改一处会立刻产生两个说法）。

## 三、工作流

1. **读材料**：梳理用户能看到的界面、按钮、提示语和真实反馈。
2. **写草稿**：先保证每步可执行，不纠结措辞。
3. **改文法**：按第一节的规则逐句改，拆长句、换动词、去术语。
4. **改元素**：按第二节的规则逐处检查 Markdown，删掉装饰性元素。
5. **自检**：按质量门禁逐项确认后输出。**先清 [阻断] 项，再看 [建议] 项** —— 建议项不是 KPI，不要为了「都勾上」去硬拆合规的句子或删掉有用的强调。
6. **验证**：按下一节「改完怎么验」三条执行 —— **改完不验等于没改**。

## 四、改完怎么验

写对不等于改对。段落、列表、示意类改动，**改完必须验**，三条缺一不可：

- **看渲染，不看源**：段落 / 列表 / 终端示意的改动，构建后抽查生成的产物（HTML 或目标渲染格式）。很多静态站点默认 `breaks: false`（连续行并成一段），源码里看着分了行，页面上仍是一整段。
- **重复内容用计数验**：`grep -c '<关键短语>'`。数量与预期不符 = 漏删或漏同步（改完只在源码里多看一眼，往往发现不了「旧句还在」）。
- **同源改动两处一起验**：改完对两处做逐字比对（`diff <(grep … A) <(grep … B)`），别只看「两处都改了」。

这三条的共同点：**用机械手段验证，不靠回看时的手感**。手感会漏，计数不会。

## 五、质量门禁

每条前面标 **[阻断]** 或 **[建议]**：**阻断 = 会让读者做错/看不懂，必须改**；**建议 = 读起来更顺，可留可改**。评分时不要用「建议项数量」衡量质量，否则会把好内容改坏。

文法：

- [阻断] 全文用「你」，没有「用户」「操作者」
- [阻断] 每个操作步骤只包含一个动作
- [阻断] 没有未解释的技术术语
- [阻断] 没有营销词、套话开头、模糊指代
- [阻断] 界面文字用「」包裹且与界面一致
- [阻断] 同一事物全文叫法一致
- [阻断] 已弃用的东西保留「是什么 + 现在怎么办」，没被整条删掉
- [建议] 单句 ≤70 字，且一句里不超过 2 个动作

Markdown：

- [阻断] 标题层级不跳级，标题是用户会说的话
- [阻断] 有序列表只用于有先后的步骤，无序列表只用于并列项
- [阻断] 表格只用于多行多列对应关系
- [阻断] 行内代码只用于「需要原样复制的内容」（命令可以；文件名、配置名、按钮名不行——按钮/菜单用「」）
- [阻断] 提示块不超过两个，且确认渲染环境支持
- [阻断] 没有装饰性分隔线、emoji 和折叠必读内容
- [阻断] 终端/输出示意只描述紧邻那条命令的后果；多步后果分开写
- [阻断] 同一内容出现在多处时逐字一致（或改为引用）
- [建议] 加粗只标「读者会因此避免一次返工/事故」的地方；同段落 ≤2 处（并列列表项各一处允许）
- [建议] 段不超过 4 行；中文标点统一；数字与单位空格一致

## 六、禁止事项

- 不规定也不需要遵守固定的章节顺序，但每一节的写法必须符合本规范
- 不用「本文档介绍了……」开头
- 不解释功能背后的原理
- 不在一个步骤里让用户做两件事
- 不用 Markdown 元素制造视觉热闹
- 不编造界面上的按钮名或提示语
