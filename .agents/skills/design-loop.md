# 设计循环（灰模先行 · 外视评审）

> 触发：设计类需求（BR1 = 新增/改版界面 · 交互流程变更 · 视觉规范变更）开工前读取；PM 开工一问答「先灰模」或未答时必读。
> 分工：报告骨架 9 项与降级阶梯单源在 @.agents/skills/uiux-design.md；本技能只管**顺序、确认点与判据**，不复述骨架。

## 一、路由表（先判类型，再决定走几步）

判据只看「改动落在哪一层」，按 **R1→R6 顺序取首个命中**。R3 与 R5 会叠加（既有页要给多版时两条都在）：顺序取 R3，**但必须继承 R5 的基线步，选定方向后按 R5 全步档走** —— 所以口径是「顺序消解 + 继承」，不是定义互斥。一条都不命中 ⇒ 按 **R5 轻量档**兜底（基线 + S3 / S4），**不得**兜底成新界面。

- **R1 小改动** —— 只改**取值**：同一属性、同一结构、同一状态集合，只换文案 / token 值 / 间距档 / 颜色值（**含组件内多态取值**，如主色与 hover 底色一起换）；**局部 / 零星取值**才是 R1，**整套字阶 / 间距 / 配色的系统性重定不算 R1**（归 R5，即使结构不变）。
  - 走 S3 → S4；可略 S1 / S2 / S5；无确认点，S4 的视觉验收四判据必过。
- **R2 新界面** —— 新增页面或新增流程，且**单方向**（只给一版组织）。
  - 走 S1–S5 全步；CP1 / CP2 / CP3 全走。
- **R3 多方向对比** —— 同一屏要 ≥2 个**组织**方案并排给用户选（判据是「要不要并排多版」，不是「新增还是改版」）。
  - 走 S1 → S2 出 2 版（上限 3 版）→ 用户选一版 → S3–S5；**既有页面先做 R5 的基线盘点，选定方向后按 R5 全步档走**；CP1 / CP2 必过。
- **R4 单组件打磨** —— 重做**一个**组件的**外观或状态集合**：新增 / 删除状态、新增伪态（hover / focus / disabled）、改尺寸 / 圆角 / 结构；只换取值不算（那是 R1）；动 ≥2 个组件 ⇒ 归 R5。
  - 走 S2′（只画该组件的状态矩阵与尺寸，不重排整屏）→ S3 → S4；可略 S1 / S5；该组件跨屏复用时 CP2 必过。
- **R5 存量优化** —— 既有页面上：动区块层级 / 向既有页面**新增 ≥1 个区块或组件** / 动视觉系统（**整套字阶 / 间距 / 配色任一被系统性重定**）/ 重做 ≥2 个组件。
  - **轻量档**（只新增或替换一个区块**或一个组件**、且不改序）：基线盘点 → S3 → S4，可略 S1 / S2 / S5。
  - **全步档**（动层级 / 一次新增多个 / 动视觉系统 / ≥2 组件）：基线盘点 → S1–S5 全步；S4 必须给「基线 → 改后」对照；CP1 / CP2 / CP3 全走。
- **R6 只读评审** —— 只出信号与位置，不改稿、不给改法。
  - 走 S4 的识别（信号 → `文件:行` 或「视口 + 区块名」）→ S5 的外视口径（§五，但不产出规格）；可略 S1–S3；无 CP，结论交 PM。

**边界判例**（五类最易混，按「取值还是系统 / 状态集合 / 组件数 / 版数 / 新增还是既有」分开）：

- 「登录按钮主色 A 换 B」⇒ R1；「主色 + hover + 禁用三处底色一起换、结构不动」⇒ 仍 R1（同一状态集合内的取值）。
- 「卡组件新增一个禁用态、圆角改档」⇒ R4（改状态集合 / 结构，哪怕只一个组件）；「同一事碰上两个组件」⇒ R5。
- 「既有列表页新增筛选栏、不调区块序」⇒ R5 轻量档（基线 + S3 / S4）；「还调了区块序」⇒ R5 全步档。
- 「既有设置页给 2 个组织方案」⇒ R3，且先做 R5 的基线盘点；「新增一个页面只给一版」⇒ R2。
- 「把全站字阶从 5 档重定为 7 档」⇒ R5 全步档（整套字阶被系统性重定，单类也算）；只改某一档的数值才是 R1。

## 二、设计循环（5 步 + 3 个确认点）

- **S1 屏幕角色句**（CP1）—— 一句话写清「这屏在 **<何时>** 帮 **<谁>** 完成 **<什么>**；**<哪件事>** 不在这里，它属于 **<哪一屏>**」。PM / 用户点头才进 S2；**缺角色句 ⇒ 交付未完成**；连这句都写不出 ⇒ 回 PRD 要范围，不靠形容词硬凑。
- **S2 组织**（CP2）—— 灰模或组织方案（§三）定区块序列、主次与交互入口；**上色前必须有这一步的组织确认**。
- **S3 上色** —— token / 字阶 / 间距 / 状态矩阵 / 断点，按报告骨架 9 项给数值（骨架见 @.agents/skills/uiux-design.md §一）。
- **S4 实现后自查** —— 反 AI 味清单第二遍（信号 → 定位到具体区块）+ 视觉验收四判据（§六）。
- **S5 外视评审**（CP3）—— 按 §五 派无上下文会话 → 拿回信号清单 → 与 PM 逐条确认，**只改确认项**；未确认的记进偏好页（§七），不夹带。

三个确认点 = CP1 屏幕角色句 / CP2 组织 / CP3 外视修正清单。任一 CP 未过就进 S3 或 S4 = 流程违规，不许「先做后补」。

## 三、灰模规格（上色前定组织）

- **形态**：ASCII 线框（单屏 ≤40 列 × ≤20 行，等宽可读）或文字区块序列（区块序号 + 主次 + 交互热点编号），二选一。
- **禁**：颜色、字体名、品牌文案、阴影 / 圆角等视觉取值 —— 灰模只回答「放什么、谁先谁后、入口在哪」。
- **判据（可勾）**：① 相邻区块的组织差异肉眼可辨（主次、序列或入口位置不同）；② 标出主任务入口与 ≤3 个热点；③ 每屏一句角色句在案（S1）；④ 不含任何视觉取值。
- **何时给两版**：同一屏有 ≥2 种合理组织（如「列表优先」vs「详情优先」）或命中 R3 ⇒ 给 2 版、上限 3 版；多版必须同屏、同断点并排，便于直接比。

## 四、参考→概念非复制（黄金律）

- **黄金律**：参考只借**方法**（层级关系、节奏、信息密度、隐喻与交互思路），不借**成品**（配色、字体、原样版面、图片、图标库）。照搬别人的视觉 = 另一种 AI 味：看不出这屏为谁而做。
- **出处留痕**（设计报告必填三行，缺一行 = 报告未完成）：
  - `参考了什么` —— 来源（链接或作品名）+ 看的是哪一屏 / 哪一段。
  - `取了哪条概念` —— 一句可执行的方法（如「主区块宽度是次区块的 2 倍，压出主次」），不写「感觉很好」。
  - `丢了什么视觉` —— 明确列出不跟随的部分（配色、字体、版面、插画风格）。
- **边界**：参考图只作分析，不导入仓库、不进交付物；不引用第三方原文，来源只在文件末尾写一行方法来源。

## 五、独立外视评审（派发口径）

- **谁来派**：PM 另派**无上下文**会话（同仓另一个 pane，任务派生 `ensure --task <编号> <角色>[@<repo>]`）；**不得复用**做过这屏的会话。样例：`bash .agents/scripts/nao-fleet.sh ensure --task T123 uiux-designer`。
- **材料信封**（只给这些，其余不给）：页面 / 路由与访问方式；视口清单；AC 编号与一句话预期；设计报告路径与实现入口；基线截图（有则给）；禁改区。
- **禁止项**：不给预期结论与判据答案；被评审方**不先解释设计意图**（防自证）；评审会话只读 —— 不改稿、不看提交历史与设计讨论、不替用户拍板。
- **派发正文模板**（逐项填，缺项 = 派发无效）：`只读评审（不改稿、不给改法、不看提交历史）。编号 T<n> · 页面 <路由> · 视口 <宽×高 或断点> · AC <编号 + 一句话预期> · 报告 <docs/designs/...> · 实现入口 <路径> · 基线截图 <路径或「无」> · 禁改区 <路径 / 区块>。` + `先给信号清单，不要先解释或复述设计意图、不要猜预期结论；回执首行写「未解释设计意图：是」。`
- **回执形状**：首行 `未解释设计意图：是 / 否`（写「否」⇒ 回执无效）；次行 `[编号] done(lite|full) | 外视评审` + 每条信号一行 = 位置（`文件:行` 或「视口 + 区块名」）+ 信号名 + 为什么（≤1 行）+ 严重度（阻断 / 应改 / 建议）；无信号写「未发现」；**只报信号，不给改法**（改法由 PM 与设计角色定）。
- **降级**：评审者无看图能力 ⇒ 只按结构、文案与数值判据出信号，回执写明「未验证实际视觉」，不判阻塞。

## 六、视觉验收（四项，缺任一 ⇒ 未过）

- **① 声明视口** —— 列出测过的视口（宽×高 或断点名）与未测视口 + 理由。
- **② 截图或降级理由** —— 每视口给截图路径；无浏览器 / 无看图 ⇒ 写「未验证实际视觉」+ 数值判据（层级 / 间距 / 对比度），不得据此判阻塞。
- **③ 空 / 加载 / 错误态** —— 三态各有可见信息与可执行动作（不只测成功态）。
- **④ 2 秒测试** —— 首屏 2s 内能答出「这屏是干什么的、下一步点哪」；无看图时以层级与文案顺序论证，结论写一句。

## 七、设计偏好持久化（跨需求）

- 载体：`docs/designs/design-preferences.md`（一仓一份，随该需求 PR 追加）。
- 三类行：`选择`（用户选了哪种组织 / 方向，一行理由）· `拒绝`（明确否掉的做法 + 理由，下次不再提案）· `例外`（本次不遵守某条基线的理由与到期复查条件）。
- **一次需求最多追加 3 行**；同类合并成一行，不写过程。
- 开工先读该页：已被 `拒绝` 的做法不再提案，除非用户明确要求（记为 `例外`）。
