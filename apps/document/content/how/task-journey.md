# 一个需求的旅程

一句话需求进，一个可回滚的提交出。中间有八站，每站都有落盘产物——会话聊久了重开，事不丢。

## 八站

1. 立项：PM 先把你的一句话问清楚，写进需求文档，开一个 Issue 做索引。产物：Issue + 需求文档。
2. 拆分排期：拆任务、定谁做谁检、定分支名，出一张开工确认卡等你点头。产物：开工确认卡 + 任务台账。
3. 起分支：研发从主干拉一条分支，先把合并请求开成草案，让检查尽早跑起来。产物：草案合并请求 + 检查结果。
4. 开发提交：小步提交，每条都带任务编号；只暂存这次改动的路径，不夹带无关改动。产物：增量代码 + 阶段文档。
5. 评审测试：测试角色按验收标准跑全量检查，出报告或你能照着点一遍的验收清单。产物：验收报告。
6. 验收合并：PM 逐条核对验收标准，并在合并请求上评论。PM 说通过才算授权，然后由研发合并，主干上只留 1 条可读提交。
7. 发布：改版本号、打标签、写发版说明（给使用者看的那份，不是提交日志）。
8. 复盘：该关的问题关掉，该记的观察带到期日记进台账，归档需求文档。

## 两条通道，别把 bug 当需求做

- fix 通道（轻通道）：能写出「期望 vs 实际」并且能复现的缺陷。免除完整需求文档，只写三行：现象、复现、回退。开工确认降为一问「现在修吗」。
- feat 通道（全通道）：新增能力、改既有行为、写不出期望与实际对比的，一律走全通道，出完整需求文档。
- 两条通道减免的是仪式，不是底线：先写能失败的用例再修、改动只碰修复路径、能一条命令回退、有人复核——一条都不减。

## 两个词：PRD、AC

- PRD（需求文档）：把「想要什么」写成一份能验收的文档，含问题证据、目标指标、范围与非范围、业务规则、验收条件、上线与回滚。它的价值不在长，而在能被人拿来判断「做完了没有」。
- AC（验收条件）：一条一句，按「前提 → 操作 → 预期」写，每条独立可测。写不出验收条件的需求，说明还没想清楚。

## 一个需求一条分支的好处

一个需求就是一条分支、一个合并请求、主干上 1 条提交。要回滚，撤销那一条提交就整批撤回；要查为什么改，读那一条提交就够了。
