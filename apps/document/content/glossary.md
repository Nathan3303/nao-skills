# 术语表

正文里出现的内部词，这里一句话说清。首次出现的地方也给半句解释，这里是全集。

## 流程词

- PRD：把需求写成一份能验收的文档，里面有问题、目标、范围、规则、验收条件、上线与回滚。它的用处是让人能判断「做完了没有」。
- AC（验收条件）：一条一句，按「前提 → 操作 → 预期」写，每条都能单独验。写不出验收条件，说明需求还没想清楚。
- 回执：干完活交给 PM 的结论单，固定含四样：做了什么、检查数字、未过项、遗留。
- 闸门：某个角色动手前必须先拿到的一份书面放行结论，由人来判。例：设计稿没经你确认，不许派前端开工。
- 门禁：能自动跑的检查，命令返回 0 才算过。它只判断机器能判断的事。
  - 门禁不是闸门：门禁看返回码，闸门看有没有那份书面结论。两者不能互相替代。
- DoD（完成的定义）：一个任务算不算完的四类判据——产物齐、验证数字齐、遗留有归口、交接写清。
- RICE：给需求打分排优先级的方法，算法是「触达 × 影响 × 信心 ÷ 成本」。
- ADR：一份「为什么这么定」的短文档，记下选型与不采纳的理由。半年后再有人问「当初为什么这么定」，答案在这里。
- fix 通道 / feat 通道：轻通道用于能写出期望与实际对比、且能复现的缺陷；全通道用于新增能力或改既有行为。减免的是仪式，不是底线。

## 舰队词

- 舰队（fleet）：就是 nao-fleet.sh 这个脚本——拉会话、看状态、回收会话都靠它。
- 角色卡：一份 Markdown，正文就是那个会话的系统提示。改动角色卡要加版本号。
- 常驻会话：pm、rd-be 这种，跨任务复用。
- 派生会话：一个任务开一个，验收完就回收。任务号不进名字，只记在元数据里；要按任务找记录，用 `nao-fleet.sh logs <角色> --task <编号>`。
- scope（已弃用）：旧版用来区分仓库的会话名后缀（rd-be@api）。现在放置键恒为仓基键（每个仓一个 workspace）；--scope、--fleet 或 .agents/fleet-scope 写了只打一行提示，然后被忽略。
- 终端后端：装角色会话的容器，只有 herdr。同一个会话就是一个 herdr 标签页（旧 tmux 后端已在 0.28.0 移除）。
- 体检（check）：静态自检命令，返回 0 才能开工。
- 插件：给 pi 加能力的 npm 包。舰队要 5 个，其中 pi-intercom 是必需的那个。
- 机制包：npm 包 nao-fleet，角色卡、清单、技能、协议都在里面；项目里只有一个转发入口。
- pin：.pi/settings.json 里记的机制包版本，跟着仓库走，团队 clone 下来就是同款。

## 契约词

- 契约：对外的行为承诺，包括接口怎么取数、错误怎么报、语义怎么定（接口就是对外的取数入口）。改契约要写影响面。
- 负向闭环：证明「该失败的东西确实失败了」的验收项。只测成功路径，等于没测。
- 先红后绿：修 bug 前先写一条能失败的用例（红），修完它变绿。这证明修的是这个 bug，不是别的东西。
- 降级：环境不满足时的替代做法，比如没装 gh 时改走本地分支。降级要显式说明，不能静默生效。
- 遗留三出口：每条遗留当场归到「关闭 / 接受（含到期日）/ 转办」三者之一，不许「先记着」。
