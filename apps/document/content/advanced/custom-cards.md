# 自定义角色卡

七个角色不够用时，加一个。角色卡就是一份 Markdown——它的正文就是那个会话的系统提示。

## 卡长什么样

```markdown
---
description: 代码评审角色（一句话说清它是干什么的）
role: code-reviewer
version: 1
updated: 2026-01-01
---

# 代码评审

## 一、职责
……
```

四件事必须齐：

- `role`：唯一 id，也是会话名的前缀。
- `version`：改内容就加 1。同一版本对应两份内容就是违规，事后无法分辨谁对。
- `updated`：改动的日期。
- 正文：写它该干什么、不该干什么、输出什么格式、遇到分歧怎么升级。写成「给一个刚入职的同事看」的口气，比写成口号有用。

## 两种加法

一、加进常驻清单（长期角色）

1. 卡放进 `.agents/prompts/<file>.md`（机制包里那份，需要你 fork 或 overlay）。
2. 在 `.agents/roles.yaml` 里加一段：id、别名、卡文件名、工作区。
3. 跑 `check` 确认清单与卡能解析、`role` 与 id 一致。

二、一次性会话（临时角色，推荐先这样试）

```bash
.agents/scripts/nao-fleet.sh ensure --card .agents/prompts/code-reviewer.md --task T7
```

- 卡必须放在你仓库的 `.agents/prompts/` 下，文件名以 `.md` 结尾，大小不超过 256 KiB。
- 一次性会话不进 `roles.yaml`，也不算常驻；用完 `close --task T7`。
- 卡里的 `role` 不能与常驻角色 id 或别名撞（会被拒）；`--as` 也只接受以卡 `role` 为前缀的名字。

## 写卡的三条经验

- 先写「不管什么」。角色跑偏，通常不是因为不知道该干什么，而是因为顺手把别人的活干了。
- 把回执格式写进卡。没有格式约束，回执就会退化成「已完成」。
- 把升级条件写死。像「涉及不可逆动作必须先要你书面同意」这类话，写在卡里比写在口头约定里可靠。

## 一句提醒

卡是完全可信输入——能改你仓库的人本来就能定义角色。舰队只校验目录、文件名、大小与命名一致性，不做内容安全审查。别装来源不明的卡。
