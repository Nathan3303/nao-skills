# ADR：设计技能的职责分层（frontend-design 管新建 · design-loop §八 管重构）

- 状态：已接受（待落地 · 随 Issue [#172](https://github.com/Nathan3303/nao-skills/issues/172) 合并）
- 更新：2026-11-24
- Owner：arch-designer
- 指针：Issue [#172](https://github.com/Nathan3303/nao-skills/issues/172) · 裁决对象 `.agents/skills/frontend-design/SKILL.md` 与 `.agents/skills/design-loop.md` §八 · 触发面 `.agents/prompts/frontend-developer.md` v15 · 门禁 `tests/t4/cases/42-design-loop.sh`

## 背景

- 两只技能都在管「别产出 AI 默认样式」：`frontend-design`（anthropics/skills，2026-09 引入）在**写码前**给方向、compact token 计划与反模板 calibration；`unslop`（CC-BY-4.0）在**写码中**按九遍把既有界面从「能跑」修到「像做过设计」。
- 冲突面是**触发条件**而不是主题：两者都只在「动界面」时想被读，于是要么两份 checkbox 抢同一段注意力，要么靠记性决定读哪一份 —— 两者都会衰减。
- 硬约束：本仓零网络（上游的抓活站 / 截图 / 故事视频三件套要 Playwright + 浏览器 + ffmpeg，不可引入）；`design-loop.md` 现 87 行、上限 120 行，**不新增文件**承载；署名是 CC-BY-4.0 的硬要求。
- 用户已排除其它形态（替换 / 合并），要的是**可判定**的边界，不是结论句。

## 决策

按**阶段与输入**分层，不按主题分层：**改动前有没有可对照的成品**，决定读哪一只技能。

- **新建档** ⇒ 读 `.agents/skills/frontend-design/SKILL.md`：方向 + compact token 计划 → 按 brief 复核 → 写码。**不读九遍。**
- **重构档** ⇒ 读 `skills/design-loop.md` §八：审计 → 方向五行 → 停 → 九遍 → 复查。
- 两者共用一条原则：**方向未定不写码**。除此之外各自成套，不互相引用条款（防双源）。
- 九遍**不新增路由**：走几步仍由 §一 R1–R6 定，§八 只替换 S3（上色）/ S4（实现后自查）**怎么做**；R1（只换取值）与 R4（单组件打磨）不读九遍。

## 判据（可对提交直接归档）

判据只看提交里的两件事实：**文件变更类型**（`A` 新增 / `M` 改动）与**改动前有无基线**。三条互斥、可枚举，第三方只读本表即可归档，不必读散文。

| 档位 | 判据（全部成立才归此档） | 反判据（出现也不改变归档） | 必读 |
| :--- | :--- | :--- | :--- |
| **新建档** | 该屏的渲染文件（页面 / 路由 / 组件）在本次提交中为**新增**（`git diff --diff-filter=A` 命中），且改动前同路由**没有任何可对照成品**：无历史版本、无已合入实现、无基线截图、无活站 | 需求原话是「重做 / 重新设计」但无成品（仍属新建）· 改动行数多少 · 产出「像不像 AI 生成」 | frontend-design |
| **清洁档**（重构） | 基线成立（既有文件改动 `M`，或活站 / 基线截图任一），且**信息集合与区块序列不变**：只动取值、间距密度、层级主次、状态集合与视觉 | 只换文案 / 只换 token 值（先走 §一 R1）· 只动单组件外观或状态集合（走 R4）· 「改动很小」 | §八 + §一 路由表 |
| **改版档**（重构） | 基线成立，且**新增或删除区块、或区块序改变**（含整套字阶 / 间距 / 配色被系统性重定） | 「只加了一个区块」不因此变新建档 · 「结构没动」不因此变清洁档（看序列，不看数量） | §八 + §一 路由表 |

- **一条 PR 两种都有**：按「该屏的路由/页面是不是此前不存在」一刀切，一屏只属一档；两屏混合就分两次派生，不在一屏内混用两套方法。
- **反判据的共同理由**：AI 味强弱是**审计的产出**，不是输入的属性 —— 用它判档会把「这屏有多糟」和「该用哪套方法」混成一件事。
- **归档结果写进派单**：PM 在派发里带一个档位词（`新建` / `清洁档` / `改版档`），RD 不再自判；判错按该 PR 的设计报告缺陷处理，不静默换方法。

## 谁在何时读 §八

分层若没人照着用，等于没做。触发点只放**会被读到的位置**，不放 ADR 与 PRD（历史文档不承担日常唤起）：

1. **卡内指针**（主入口）—— `.agents/prompts/frontend-developer.md` 按需技能块那一行：`design-loop.md §八`，写明「重构既有界面先归档，新建不读九遍」，与 `frontend-design` 那一行并列且互指职责；§四 再行内补一句同口径。`uiux-designer.md` 不动（§二 S3/S4 已在它的循环口径里）。
2. **技能内文**（兜底）—— §八 首句自带适用条件与「新建页面不读本节」。
3. **机器闸门**—— `tests/t4/cases/42-design-loop.sh` 三条断言**各自承重**：主入口锚点（rd-fe 卡按需技能块行首，仅留 §四 回声不算）· §八 节标题在位（指针目标存在）· §八 节内条目数下限（整节被删或被掏空即红）。
4. **显式口径**：**新建页面不读九遍，只走 frontend-design**。新建场景被要求做审计或逐遍清单 ⇒ 属误用，按上表反判据自查，不另加流程。
5. **可用性验收判据（半年后的检验）**：把一条真实提交贴给任一 rd-fe 会话，不提示、不指路，它能归到三档之一并说出依据 —— 做不到即本分层失效，须回到触发点位置重写，而不是加条款。

## 理由

1. 业务匹配：两类工作的**输入**根本不同 —— 新建没有可审计对象（无 `文件:行`、无基线可比），重构必须先有基线。分层切在输入上，判据就能落到 diff 上。
2. 成熟度：两侧都是既有实践；本批只搬方法内核（顺序与判据），不引进新工具、不新增依赖。
3. 团队能力：两处入口各一行指针，rd-fe 读一次即知自己是哪一档；无需背两套 checklist。
4. 成本：正文 +13 行内容（§八），并 §四 三条留痕为一行 −3 行，净 **87 → 99 行**（上限 120 未动，余 21）。

## 对照过的备选模式

1. **维持现状（两份并存，靠自觉，基线）** —— 适用：两者的触发条件天然互斥；代价：无。**不采纳**：实测触发条件重叠，且没有任何判据能说「这次该读哪一份」—— 这正是本批被立项的原因。
2. **替换（用 unslop 方法取代 frontend-design）** —— 适用：新建也总能拿到基线；代价：丢掉「写码前 token 计划 + 按 brief 复核」。**不采纳**：九遍的起点是审计清单，新建屏没有可审计对象 ⇒ 只能退化成「无输入硬造方向」，比现状更差；且丢掉 anthropics 侧的 calibration 与「方向未定不写码」的复核闸门。
3. **合并成一份** —— 适用：两套方法能压进 120 行且不产生第二套分类；代价：单文件兼管两个入口。**不采纳**：新建面 73 行 + 九遍约 30 行 + 共用件必然爆上限；更严重的是会与 §一 R1–R6 路由表并存成**第二套分类**（按「新建/重构」一套、按「值/系统/组件数」一套），正是本批要治的双源。
4. **分层（采纳）** —— 适用：新建与重构的输入不同、产物不同、验收点不同；代价：两个入口，靠卡内一行指针消歧，并需一条用例咬住指针不丢。判据见上表。

## 吸收边界与署名（CC-BY-4.0 合规）

- **只取方法内核，中文重写**：审计 → 方向五行 → 停 → 九遍（顺序理由：间距定节奏；文案定字号与位置；视觉与动效最后）→ 复查含换名测试。**措辞如实**：方法内核为本仓中文重写、无整段照译；个别公式与档位表述（⑦ 内圆角、⑤ 字重档）与上游高度接近 —— 这些属规格/取值，署名在案。未含上游三项特征原句（闸门：`cases/42` 三条特征串在 `.agents/**` 0 命中）。
- **未并入**：上游 `SKILL.md` 正文与 `references/*.md`（原文，非方法，重写即可覆盖）；5 张 `.webp`（图片，属成品）；`scripts/snapshot.mjs`、`story.mjs`、`story-path.mjs`（需活站抓取 + Playwright + ffmpeg，与本仓零网络冲突；本仓 §五 外视评审的材料信封已承担「基线对照」职责）。
- **署名**：`design-loop.md` 文末**单点**（`grep -c '方法来源'` = 1，含三仓名 + 许可 + 作者 + 链接 + 访问日期 + 改动说明）+ `README.md`「设计技能与致谢」一段（用户向 3 行）。不在文件头再挂许可段：技能正文是方法面，合规面在本节。
- **行数**：§八 13 行内容 + 标题与空行；§四 三条留痕并一行（−3）；实测 87 → 99，上限 120 与 §三 / §五 / §六 判据均未动。

## 后果与风险

- 正面：两个入口各有判据，rd-fe 不必背两套清单；九遍集中在「有基线」的场景，工作量与收益匹配。
- 负面：多一层归档动作（一行档位词），PM 派单需带上。
- 风险：分层靠指针唤起 —— 指针被删则退回「靠记忆」，故用 `cases/42` 三条断言（主入口 / 节标题 / 节内条目数）+ §八 首句兜底；指针若只留在卡里，下游仓自建卡可能漏读，属已知边界。
- **观察项（到期 2027-05-24）**：本仓无 UI，ADR 内不写真实页面例子（臆造的例子会成为「看起来验证过」的假证据）；下游仓首个设计类需求落地后回填三条真实提交（新建 / 清洁档 / 改版档各一），用于验证上表判据不重叠。
- 本批**不 bump 版本、不打包**（版本号与 `docs/releases/` 属发行批次，另派）。

## 限制与已知边界

- 不覆盖：新建档是否也要逐遍自查（不适用 —— 无审计对象）；R1 / R4 单点调整是否强制九遍（不强制）。
- 未吸收上游的 `rtl.md`（右到左细则）、图像生成、故事视频（需网络或图像工具，本仓零网络）。
- 判据只看「文件变更类型 + 基线有无 + 区块序变否」三件事；**设计质量本身不在本 ADR 判定范围**（归 §六 视觉验收与外视评审）。
