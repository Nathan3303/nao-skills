# PRD · 开工确认卡表格化 + 台账按批次分割

- 任务：**T580** · Issue [#238](https://github.com/Nathan3303/nao-skills/issues/238) · 分支 `nao/T580-kickoff-ledger`
- 类型：机制约定 + 文档结构（含 `check` 最小断言）
- 依赖：**T579 先合并**（本任务的 `kickoff.md` 落在任务目录里，靠 T579 的目录约定）

## TL;DR

开工确认卡从「对话里的一次性文字」变成**表格化、独立落盘**（`docs/<任务号>-<slug>/kickoff.md`），台账只放**卡摘要 + 指针**且**任务完成后必须删掉**；台账本身按批次切成 `##` 二级标题，新增**流转状态（6 值枚举）**与**完成日期**两列，805 行存量整体搬进 `tasks-archive.md`，主台账只留活批次。同时把「卡片可用表格 / PRD 与报告正文仍禁表格」这条边界写死，消灭两规矩打架。

## 一、问题证据

- **卡不落盘 ⇒ 无法回看**：开工确认卡历来只出现在对话里。跨会话重开（本仓今天已发生过多次）或三天后回看，谁都不知道当时确认了什么、确认了哪几项；`docs/tasks-state.md` 里也没有对应记录。
- **台账结构性病**：805 行；开头挂着 100 余行**无标题**的历史 bullet，然后才是 `## PM 接续快照`；批次段用 `###` 与 `##` 混排；「待派发队列」「观察/定时/已接受」「进行中」三节与实际状态早已不同步（实测：T562 行仍留在「进行中」表里，而它 2026-11-24 就合并并发布；T579 全流程无任何台账行）。
- **没有「完成」这个事实**：现在的表只有「派发时间 / WIP 提交」，看不出一个任务卡在哪一步（未开工 / 进行中 / 待验收 / 已合并 / 已发布 / 已关闭），也无法回答「这周完成了几个」。
- **完成项继续占空间**：已完成批次的卡内容与指针仍留在台账里，文件只增不减 —— 用户 2026-11-27 明确要求「完成后必须删除」。
- **两规矩打架（已知冲突）**：`deliverable-docs.md` §三 规定「PRD/报告正文禁表格」，而本任务要求开工卡用表格 ⇒ 必须划清边界，否则以后 RD/QA 判不清一条表格算不算违规。

## 二、目标指标

- **卡可回看率 100%**：新批次任务都有 `kickoff.md`，且台账该批次段有卡摘要（字段完整率 100%）。
- **台账可读性**：主 `tasks-state.md` 行数从 805 降到 **≤ 300**；批次段一律 `##`，活批次数 = 二级标题数（可机判相等）。
- **状态可查**：任一活批次能在台账一眼看出 6 值状态之一 + 完成日期；状态值域外写法 **0 处**。
- **完成即收**：任务完成后 24h 内，台账里该批次的卡摘要与指针消失（**kickoff.md 文件本体保留**，只是不占台账），可机判。
- **规则冲突 0**：`deliverable-docs.md` 明确「卡片/台账可用表格，PRD 与报告正文仍禁」，并有断言钉住。

## 三、范围 / 非范围

**范围内**

- 开工确认卡模板：固定 **10 个字段**（任务号 · 目标一句话 · 角色链 · AC 指针 · 门禁 · 红线 · 待澄清/待拍 · 设计类与否 · 发布节奏 · 用户确认结论），**表格形态**。
- 落盘规则：卡全文进 `docs/<任务号>-<slug>/kickoff.md`；台账该批次段内嵌 **6 行卡摘要表**（任务号/目标/角色链/状态/完成日期/卡指针）。
- 台账结构：`## <批次标题>`（一个活批次一个二级标题，标题含任务号）+ 该批次下的摘要表与交付记录；**历史批次整体搬 `docs/tasks-archive.md`**，主台账顶部保留「批次索引」表（任务号 → 归档锚点）。
- 台账列：**流转状态**（`待开工` / `进行中` / `待验收` / `已合并` / `已发布` / `已关闭`，恰 6 值）+ **完成日期**（`YYYY-MM-DD`，未完则 `—`）。
- 完成即收：状态进入 `已合并` / `已发布` / `已关闭` 后，删台账里的卡摘要与指针（保留 kickoff.md）；台账顶部**保留一行批次索引**（任务号 → 归档锚点，用户 2026-11-27 拍）。
- **工作区纪律（今天实证 · 采纳 T581 F19 的口径）**：**禁**在共享工作区 `checkout` / `switch` / `stash` 别人的未提交改动；**需要切分支或并行写作时**必须 `git worktree add`；同一工作区只有一个写入会话时可直接工作（不强制一刀切）。配套 warn-only 软闸：`.git/worktrees/` 非空或 `git status --porcelain` 非空 ⇒ 一条提示，不改 rc。正文落 `github-flow.md` 工作区节（单源），角色卡只留指针。
- 规则边界：`deliverable-docs.md` §三 补一段「表格适用范围」。
- `check` 最小断言：台账结构（二级标题即批次、状态值域、卡摘要字段齐全、完成项无残留指针）+ 卡文件存在性（warn-only，判红归 `tests/t4/cases/54`）。

**范围外**

- 不改 `docs/README.md` 索引结构（T579 已定）。
- 不迁历史目录（T579 已定冻结）。
- 不改发版节奏、不改卡内其它条款（那是 T581 Review 的输入，不是本任务）。
- 不重写历史批次的**内容**（只搬位置，不改事实；搬动时只允许去重与标题化）。

## 四、用户场景

- **PM 开批**：出卡 → 写 `kickoff.md` → 台账加 `## <任务号> · <slug>` 段 + 6 行摘要 → 派单。用户在任何时候打开仓库都能看到「这批确认了什么」。
- **用户回看**：三天后问「T580 当时确认的发布节奏是什么」，`docs/T580-kickoff-card/kickoff.md` 一屏作答，不必翻对话。
- **PM 收尾**：任务合并/发布后，把状态改成 `已合并`/`已发布` + 填完成日期 + 删卡摘要与指针 ⇒ 台账回到「只有活批次」的短形态。
- **新会话接手**：读 `tasks-state.md` 的二级标题即见在飞批次与状态，历史走顶部批次索引一步跳归档。

## 五、业务规则

- **卡即契约**：卡一旦确认，字段不得事后静默修改；要改就追加一行「变更记录（日期 · 改了什么 · 谁同意的）」。
- **状态只进不退（含唯一例外）**：6 值单调向前；若已合并后又发生关闭类事件（事故/回滚），**以最后发生者为准**（状态改 `已关闭`，完成日期 = 关闭日，变更记录写明原合并 sha）—— 用户 2026-11-27 拍。
- **完成日期语义**：`已合并` 填合并日期，`已发布` 填发布日（覆盖前者），`已关闭`（未交付即关闭）填关闭日。
- **完成即收的边界**：删的是**台账里的摘要与指针**；`kickoff.md` 与当批报告/PRD 一律保留（它们在任务目录里，本来就不占台账）。
- **历史搬家的保真**：搬进 `docs/tasks-archive.md` 的内容，只允许加二级标题与去重，事实字段（sha、Issue/PR 号、数字）一字不改；搬完主台账里每个被搬批次留一行索引（任务号 → 归档锚点）。
- **表格边界**：卡片与台账（含清单类）可用表格；`prd.md` / 报告 / ADR 的**正文**仍禁表格（多行多列对应关系可用列表 + 加粗字段名承载）。

## 六、NFRs（业务视角）

- **可机判性**：字段名、状态值域、表头逐字固定，允许脚本判定；不依赖自然语言理解。
- **不增体检时长**：新增断言使 `check` 增量 ≤ 0.2s。
- **零数据丢失**：归档后任何历史批次仍可 `grep` 到（sha / Issue 号 / 报告路径）。
- **可回滚**：单条 `git revert` 回退到「旧台账 + 无卡文件」状态，不产生「台账新结构 + 无卡」的半启用。

## 七、AC

### 主路径

**AC1 · 开批即有卡与摘要**
Given 一个新批次 T999，When PM 写 `docs/T999-x/kickoff.md`（10 字段齐）并在台账加 `## T999 · x` 段 + 6 行摘要（状态 `进行中`、完成日期 `—`），Then `check` rc=0 且台账结构断言零 warn，`check -v` 显示该批次已登记。

### 异常

**AC2 · 非法状态值必报**
Given 台账某行状态写成 `搞定了` 或 `done`，When 跑 `check`，Then 点名该行「状态值域外（应为 6 值之一）」，并给出合法值清单。

**AC5 · 完成后残留必报**
Given 某批次状态已是 `已发布`，When 台账里仍保留卡摘要表或 `kickoff.md` 指针（且不在「变更记录」里），Then `check` 点名「已完成批次仍占卡摘要/指针」。

### 负向闭环

**AC3 · 卡字段缺失必报**
Given `kickoff.md` 缺 `发布节奏` 字段（或表头被改），When 跑 `check`，Then 点名缺失字段名；补回后归零（先红后绿各一次）。

**AC6 · 目录有卡而台账无行必报**
Given 存在 `docs/T998-y/kickoff.md` 但台账无 `## T998` 段，When 跑 `check`，Then 点名「有卡无台账行」。

### 边界

**AC4 · 历史搬家保真**
Given 搬家前后，When ① 对比 `grep -c` 血统字段（各批次 sha / Issue 号 / PR 号 至少各 1 处可命中）② 主台账行数（目标 ≤300）③ 归档文件二级标题数 = 被搬批次数，Then 三者全部满足，且主台账顶部批次索引能一跳定位任一历史批次。

### 设计一致性

**AC7 · 表格边界不互相打架**
Given `deliverable-docs.md` 新边界（卡片/台账可用表格，PRD/报告正文仍禁），When ① 对一份正文含表格的 `prd.md` 跑结构探针 ⇒ 仍点名（不放松）② 对 `kickoff.md`/台账用表格 ⇒ 不报违规，Then 两向都成立。

**AC8 · 判红载体归位**
Given 台账/卡断言，When 删掉台账里某批次的一行（或改坏 kickoff 表头），Then `tests/t4/cases/54` **必红**；`check` 只 warn-only 不改 rc（同 T579 口径，防「`!` 行永不改 rc」的假绿）。

**AC11 · 工作区纪律落文本（不作假机判）**
Given 机制文本，When ① 工作区纪律正文在 `github-flow.md` **恰 1 处**（含「`git worktree add`」「禁在共享工作区」两个短语）② 各角色卡只出现指针（不复制正文）③ 一条静态断言能判断「删掉该段 ⇒ 必红」，Then 三者成立。
**明示**：这是**纪律型条款**，不承诺机判「是否真用了 worktree」；只机判「规矩还在、且单源」—— 够用，不造恒真命令。

**AC9 · 本任务自身即样板**
Given 本任务合并后，When 执行 `ls docs/T580-kickoff-card/`，Then 含 `prd.md` + `kickoff.md`（本卡即为表格形态的样板），且台账里有 T580 段（状态如实）。

### 上线闭环

**AC10 · 发布可用**
Given 本任务随版本发布，When PM 发版，Then `kickoff.md` 的 `发布节奏` 字段与实际一致（MINOR/PATCH 不改口），且台账 T580 段在发布后按「完成即收」处理（状态 `已发布` + 完成日期 + 删摘要指针）。

## 八、上线闭环

- **发布节奏**：MINOR（机制文本 + 台账结构 + `check` 新断言；0.x 下按 MINOR）。
- **回滚**：`git revert <合并 sha>` 单条；回退后台账回到旧形态、卡文件成孤儿（不参与任何断言），不产生半启用。
- **台账**：本任务自身的台账行按**新结构**登记（首个实例），T579/T580/T581 三行一并归位。
- **迁移说明**：`docs/INSTALL.md` 补一句「台账与开工卡怎么摆」指针到 `deliverable-docs.md`（只指针）。

## 九、变更治理

- **谁定**：卡字段与台账结构正文归 PM（`deliverable-docs.md` / `pm-operations.md`）；`check` 与 `cases/54` 归 `rd-infra`；卡模板归属看 T581 结论。
- **怎么改**：新增卡字段或状态值，必须同时改 ① 正文 ② `check` 断言 ③ 模板 ④ 本 PRD §五，缺一视为未完成。
- **已拍（2026-11-27）**：① 完成项**保留一行「批次索引」**（台账顶部索引表，不进批次段）② `已关闭` 与 `已合并` 并存 **以最后发生者为准**（变更记录保留原合并 sha）。
- **开工闸门**：用户 2026-11-27 确认「现在开工」并授权无人值守；落地排在 T579 合并之后（两者改同一批机制文件，串行）。
