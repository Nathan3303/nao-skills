- 指针：Issue [#51](https://github.com/Nathan3303/nao-skills/issues/51) · 来源 = L1 复盘 `docs/reports/2026-10-28-T529-retro.md` §四（三条防线）· 现行框架 `tests/t4/lib.sh` / `tests/t4/run.sh` · 发布闸门 `.agents/skills/github-flow.md` 阶段 7 · PM 卡 `.agents/prompts/product-manager.md` v26

## TL;DR

- **做什么**：把 T529 复盘的三条防线落成机制 —— ① `full` 口径 **NOTE 白名单制**（非白名单 NOTE 即 FAIL）② PM 卡增「**根因派发须附实测命令**」纪律 ③ 发布前置改 **双环境 gate**（`$TMUX_PANE` 已设 / 未设都要绿），并封装 `npm run test:t4:full:dual`。
- **给谁**：PM（②）、QA/RD 与发布执行人（①③）、后续维护者。
- **成功标准**：非白名单 NOTE 在 full 下必然 rc≠0（负控翻红）· PM 卡 v27 · `test:t4:full:dual` 实测两组皆绿 · `check` + `npm test` rc=0。
- **不做什么**：不改任何用例的断言语义（只加 tag）· 不改 `nao-fleet.sh` · 不加新依赖 · 不动 CI/流水线阶段数量。

## 一、问题证据

- **NOTE 掩盖通道**：`t4_note()`（`lib.sh:80`）只打印 `[NOTE]`，`run.sh` 仅计数（`:155`）；而 `full` 的判据只含 SKIP/DEGRADE（`github-flow.md:56`）⇒ **能力缺失时可以跳过断言而不阻断**。T529 的 `cases/09` 正是这样：真回收断言可能从未执行却报绿。
- **现有 NOTE 点 4 处**：`cases/06:51`、`cases/06:63`（静态替代证据）、`cases/07:17`（pin 未发布 → 用 latest 做布局对照）、`lib.sh:219`（CLI 缺 `migrate` → 走 init 迁移路径）。均为**合法的能力/前提说明**，需保留但要可区分为白名单。
- **PM 判断失真**：T529 中 PM 在无实测的情况下给出根因（「88 处 tmux 调用打默认 server」）并据此下达实现方向，被 QA 两条 A/B 实测推翻 —— 若 RD 照办将产生大范围无意义改写。
- **环境前提未显式化**：发布前置与 QA 复核都在「tmux 内、默认 socket」前提下跑，`$TMUX_PANE` 差异导致同树不同结论（QA `%5` 绿 / PM `%0` 红）。

## 二、目标指标

- **掩盖归零**：`full` 下非白名单 NOTE 计数 = 0（出现即 FAIL）；白名单命中数 ≤4 且逐条可解释。
- **负控可证伪**：注入未登记 tag ⇒ full 必红；从白名单摘除现有项 ⇒ 必红（各 1 次演练，含 md5 还原）。
- **双环境覆盖**：`test:t4:full:dual` 两组都 rc=0；`env -u TMUX_PANE` 组能复现 T529 红态（在旧代码上）。
- **纪律可核**：PM 卡 v27 含 1 条硬性（无实测不得派根因方向）；checklists 增 1 项。

## 三、范围 / 非范围

范围内：

1. `tests/t4/lib.sh`：`t4_note <tag> <msg>` 形式化（tag 必须来自白名单枚举；空/未登记 tag 在 full 下计 FAIL）。
2. `tests/t4/run.sh`：full 模式下校验 NOTE tag 并对非白名单计入 FAIL（RESULT: FAIL + rc≠0）。
3. 4 处现有 NOTE 补 tag（语义不变）。
4. `package.json` 增 `test:t4:full:dual`（两组串跑，任一红则红）。
5. `github-flow.md` 阶段 7 条款指向 `test:t4:full:dual`。
6. PM 卡 v26→v27（红线/流程 +1：根因类派发须附实测命令与输出）+ `checklists/pm.md` +1 项。
7. `tests/README.md` 增「NOTE 白名单」小节。

非范围（每条带理由）：

- **清掉 4 条 NOTE 改 SKIP**：理由 = 它们是合法前提说明（静态替代 / pin 未发布 / 缺 migrate），改 SKIP 会在 `full` 下把正常的降级路径判红，误伤面更大。
- **改 `nao-fleet.sh`**：理由 = 本批是测试框架与纪律，与舰队脚本无关。
- **改 CI/流水线阶段**：理由 = 发布执行以 `github-flow.md` 阶段 7 为准，同步措辞即可。
- **给 NOTE 加退出码语义**：理由 = 保持 `t4_note` 只打行，判定统一在 `run.sh` 聚合层（单点）。
- **追溯改写历史报告中的 NOTE 计数**：理由 = `deliverable-docs.md` §七 不追溯。

## 四、用户场景

- **场景 A（QA/发布执行人）**：跑 `npm run test:t4:full:dual` → 两组都 PASS，输出列出「白名单 NOTE 命中：3 条（tag 明细）」；若有未登记 NOTE → 直接 FAIL 并指出 tag 与用例。
- **场景 B（PM 派发根因类任务）**：先把假设写成一条命令跑一遍，把命令与输出贴进派发消息；否则只能派「诊断任务」。
- **场景 C（新作者加 NOTE）**：想在某用例跳过断言 → 必须先在白名单登记 tag 并写理由，runner 才放行；单方面 `t4_note` 会被 full 拦下。

## 五、业务规则

- **BR1 白名单制**：NOTE tag 枚举固定为 `static-contract`（静态替代证据）· `pin-fallback`（pin 未发布改对照 latest）· `migrate-fallback`（缺 migrate 走 init）；新增 tag 必须同时改白名单 + 在 `tests/README.md` 说明理由。
- **BR2 单点判定**：NOTE 合法性只在 `run.sh` 聚合层判定（不在 `t4_note` 里直接 exit），保持用例只产出事实。
- **BR3 full 才严**：非 `T4_REQUIRE_FULL=1` 模式仍只计数（不阻断），避免日常 `npm test` 因环境降级变红。
- **BR4 双环境等价**：`test:t4:full:dual` = 两组同参数跑（唯一差异 `$TMUX_PANE` 有无），任一非 0 即整体非 0，且输出标明哪组失败。
- **BR5 纪律可核**：PM 卡新增硬性条款——派发含「根因 + 修复方向」的指令时**必须附一条已执行的实测命令与输出**；无实测只能派「诊断/复现任务」。`checklists/pm.md` 交付清单 +1 项对应。
- **BR6 不放松既有判据**：SKIP/DEGRADE 判据不变（新增的是 NOTE 维度）。

## 六、NFRs

- **耗时**：`test:t4:full:dual` ≈ 2.3× 单轮（实测 139–170s，单轮 74s）· 发布前置按 ~3 分钟预算；不得让 `npm test` 变慢（默认路径不含 dual）。
- **幂等**：两组跑不共享状态；NOTE 校验纯静态解析，无副作用。
- **兼容**：`t4_note` 旧调用形式（无 tag）在非 full 下仍可跑（仅警告），full 下 FAIL —— 避免其他分支静默失效。
- **可维护**：白名单单点定义在 `run.sh`（或 `lib.sh` 常量），新增 tag 只改一处 + 文档一句。

## 七、验收标准

- **AC1（主路径 · NOTE 白名单）**：Given `T4_REQUIRE_FULL=1`，When 用例产生 tag = `static-contract|pin-fallback|migrate-fallback` 的 NOTE，Then 计数并 PASS；When 产生**未登记 tag** 或**无 tag** 的 NOTE，Then **RESULT: FAIL + rc≠0** 且输出点名 tag 与用例号。
- **AC2（现有 4 处）**：Given 现状代码，When 打 tag 后跑 `npm run test:t4:full`，Then rc=0，输出列出白名单命中明细（≤4 条），且 4 处语义未变（diff 只加 tag 参数）。
- **AC3（负控非空转）**：① 注入一条 `t4_note unknown-tag "x"` ⇒ full 必 FAIL 并点名；② 从白名单常量摘掉**当前实命中**的 tag（本机 = `static-contract`）⇒ 必 FAIL；两处即时还原 + md5 一致。（订正 2026-10-28：原文写「摘 `pin-fallback`」，但 pin 已发布时 07 根本不发该 NOTE ⇒ 照字面执行会**空转通过**；`pin-fallback` / `migrate-fallback` 的端到端验证改在隔离副本构造条件完成。）
- **AC4（双环境 gate）**：Given `package.json` 新增 `test:t4:full:dual`，When 跑它，Then 两组皆 rc=0 且输出分别标注组别；When 任一组人为制造失败（如临时破坏）Then 整体 rc≠0 并标出失败组。
- **AC5（发布条款）**：Given `github-flow.md` 阶段 7，When 读，Then 发布前置改为 `npm run test:t4:full:dual` rc=0（判据 = **两组 SKIP/DEGRADE 均为 0 且非白名单 NOTE 为 0**）。
- **AC6（PM 纪律）**：Given PM 卡 v27，When 读红线/流程，Then 含「根因 + 修复方向 派发须附实测命令与输出；无实测只派诊断任务」；`checklists/pm.md` +1 项对应；`version`/`updated` 已 bump。
- **AC7（负向 / 边界）**：Given 变更集，When 看 diff，Then `nao-fleet.sh` 零改动、无用例断言语义变更（只加 tag）、无新依赖、流水线阶段数不变；`check` rc=0 · `npm test` rc=0。
- **AC8（可用性）**：Given 能力齐备环境，When 跑 `npm run test:t4:full:dual`，Then 输出可读（组别 / 白名单 NOTE 明细 / 结论一行）；`tests/README.md` 有白名单小节；留实测输出摘要。
