# PRD：`ensure` 不再白等 60 秒（+ 同型测试管道清理 + 就绪提示）

- 状态：已交付并发布（v0.20.4）· Owner：PM · 更新：2026-11-01
- 指针：来源 = 用户 2026-10-31 实测反馈（「这个命令一定要等这么久吗？我其实已经看到 Pane 了」）+ 实测机制复现 · T535 遗留 `T535-O2`
- **降级标注**：立项时 `api.github.com` 不可达（`gh` TLS handshake timeout · `curl` rc=28），故**跳过 Issue**（无 Issue 号），分支用降级命名 `nao/t536-ensure-return`；PR/Issue 待 API 恢复后补建。
- 优先级：中高（每天用多次的命令，每次白等最多 60s）· RICE 结论 ≈ 28（附录）

## TL;DR（≤5 行）

- **做什么**：① 让 `ensure` 拉起会话后**立即返回**（不再被「60 秒后清理临时文件」的后台任务拖住），且清理行为不缩水；② 修 `tests/t4/lib.sh` 里最后一处同型 SIGPIPE 管道；③ 拉起成功后打印一行就绪指引。
- **给谁**：所有跑舰队的人（尤其用工具调用/CI 捕获输出的场景）。
- **成功标准**：经管道调用 `ensure` 返回耗时 ≈ 拉起耗时（不含 60s）且清理仍在 60s 后发生；`lib.sh` 同型管道清零；输出新增恰一行。
- **不做什么**：不改 `ensure` 的拉起方式（tmux/布局/prompt 注入）、不改 `close`/`status`、不动 `sleep 60` 的时长语义。

## 一、问题证据

- **用户实测（2026-10-31）**：连续三次 `ensure` 中有两次「pane 已出现但命令不返回」，其中一次由用户中断；用户明确反馈「命令一定要等这么久吗？我其实已经看到 Pane 了」。
- **PM 实测机制（2026-11-01 · 最小复现，同一脚本仅改输出目标）**：
  - `bash -c '( sleep 5; ) & disown; echo done' | cat` ⇒ **5.003s**
  - 同一命令重定向到文件 ⇒ **0.003s**
  ⇒ 后台任务的输出继承导致**调用方等 EOF**；即「拉起完成」与「命令返回」被解耦成两件事。
- **定位（只读行段）**：`nao-fleet.sh:1085` = `( sleep 60; rm -f -- "$prompt_file" ) & disown 2>/dev/null || true` —— 该后台子 shell 未重定向 stdout/stderr，故它活着期间持有调用方的输出管道；`disown` 只脱离作业表，**不关闭继承的 fd**。
- **后果**：① 人以为卡死并中断（中断可能影响后续步骤）；② CI/工具调用被拖 60s 甚至超时失败；③ 与「pane 已就绪」的事实相矛盾，属**信息误导**而非纯性能问题。
- **副项证据（B）**：`tests/t4/lib.sh:199` `t4_cli_supports` 仍是 `printf '%s' "$h" | grep -qE …` —— 与 T535 修掉的三处 helper 同型（QA `T535-O2`；输入 ~2KB 低于管道缓冲 ⇒ 低危但同类）。
- **5 Whys（A）**：命令不返回 ← 后台清理子 shell 持有 stdout/stderr ← 写时只想着「60s 后删临时文件」← `disown` 被误当作「彻底解耦」← 从未在「输出被管道捕获」的场景下验证过返回时机。

## 二、目标指标

- **北极星**：经管道调用 `ensure` 的**返回耗时与拉起耗时一致**（不随 `sleep 60` 变化）。
- 预期：`time bash -c 'nao-fleet.sh ensure … | cat'` 的额外等待从 **≈60s 降到 <2s**；`prompt_file` 仍在 ~60s 后被删除（行为不缩水）。
- 观测：两次实测耗时（重定向 vs 管道）与 presence/absence 断言（清理前存在、清理后消失）。

## 三、范围 / 非范围

- **范围**
  1. **A · 返回不被后台任务拖住**：让 `nao-fleet.sh:1085` 的后台清理**不再持有调用方 stdout/stderr**（实现方式由 rd-infra 定：`>/dev/null 2>&1` 重定向、`setsid`、或改用 `at`/定时器等价物；**不得**用「删掉清理」换取返回速度）。
  2. **B · 同型管道清零**：`tests/t4/lib.sh:199` `t4_cli_supports` 改 here-string；补 1 条 helper 级断言（命中/未命中两向）。
  3. **C · 就绪提示**：`ensure` 成功拉起后打印**一行**「已拉起，就绪/在线状态用 `nao-fleet.sh status` 查看」类提示；多角色一次调用只打印一次；`--task`/`--force` 等分支同样适用；失败/跳过分支不打印。
- **非范围**（各带理由）
  - 不改 `sleep 60` 的时长与清理目标：理由 该窗口用于 pi 读取初始 prompt 文件，缩短可能引入竞态；本批只解决「持有管道」。
  - 不改拉起实现（tmux 命令、布局、prompt 注入、model 白名单）：理由 与返回阻塞正交，动它回归面大。
  - 不改 `status`/`close`/归属判定：理由 T534 已定稿并落地 ADR。
  - 不引入「等待就绪」新能力（如 `--wait`）：理由 用户反馈的痛点恰恰是「不想等」；先做到「不阻塞返回」，若后续需要显式等待另立。
  - 不改 `ensure` 的 CodeGraph 状态行：理由 与本批无关，且该行是显式注入的信息。

## 四、用户场景

- **画像 A（人，终端里跑）**：命令立即返回、pane 已就绪，不再怀疑卡死。
- **画像 B（工具/CI 捕获输出）**：不再被拖 60s 或超时；日志里能看到就绪提示。
- **画像 C（批量 ensure 多角色）**：只打印一行提示，不刷屏。
- **关键路径**：`ensure` → 拉起 pane → 后台清理（脱离调用方 fd）→ 立即返回 + 一行提示。
- **页面状态**：不适用：CLI。

## 五、业务规则

- **BR1 清理不缩水**：`prompt_file` 必须在 ~60s 后被删除（原行为保持不变）；不得以「反正文件在 /tmp」为由取消清理。
- **BR2 不持有调用方 fd**：任何 `&`/`disown` 的后台任务**必须**显式重定向 stdin/stdout/stderr（脚本级自查：新增后台任务处必须带重定向）。
- **BR3 提示一行**：新增输出恰 1 行、只在成功拉起时打印、多角色只打 1 次；不得改变既有行内容与顺序（既有断言/测试依赖输出）。
- **BR4 同型清零**：`lib.sh` 中 `printf … |` 写法在本批后为 **0 处**（B 项），并保留 helper 语义等价。
- **BR5 只读变异**：B 项的语义等价验证须在临时副本上进行（不得就地改用途中断其他用例）。
- **BR6 降级标注**：本批因 API 不可达而跳过 Issue，须在 `tasks-state` 与回执中标注「降级」，PR/Issue 恢复后补建。
