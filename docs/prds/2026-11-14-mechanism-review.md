## 二、目标指标

- **主指标**：产出 1 份 ≤80 行评审报告 + 1 份问题清单（每条带 `文件:行段`）+ 1 份改进批次拆解。
- **覆盖指标**：4 个评审维度**各自**至少 3 条带行段引用的发现；某维度确无问题 ⇒ 必须写「怎么查的 + 证据」才算覆盖。
- **质量指标**：问题清单里 P1（结构性）每条都能被第三方**用一条命令或一次行段读取**验证；qa 抽查 ≥5 条行段引用**逐条可达**。
- **不发散指标**：本批 diff 中 `.agents/`、`bin/`、`tests/` **零改动**（评审不改实现），只有 `docs/` 新增。
- **可用性指标**：至少 1 条拆解直接可开工（含范围 / AC 草稿 / 主责角色），PM 看完不需要再补问。

## 四、用户场景

- **作为机制维护人（用户本人）**，我想知道「这套东西现在还有没有自相矛盾、我照它做会不会又被坑」，以便决定下一批投在哪。
- **场景 A（跨批接手）**：我 3 周后回来，需要 5 分钟内知道**哪些口径已作废**。
- **场景 B（新增角色 / 改卡）**：我要加第 8 个角色或改一张卡，需要知道**一次要同步哪几处**，否则又会出现「改一处、漏一处」。
- **场景 C（遗留三档到期）**：到期时我需要知道**哪些能合并降级、哪些必须保留**，而不是逐条重新判断。

## 五、业务规则

- **主审一人**：`arch-designer` 出唯一报告；`qa` 只做交叉复核（专攻「声明 vs 判据」落差），**不另出第二份报告**（防双源）。
- **行段强制**：每条发现必须给 `文件:行段`；无行段的意见**不得进清单**（同 T542 设计师 REJECT 纪律）。
- **两分结论**：结论必须分「**已证实**（附命令 / 行段）」与「**需实测**（谁、什么判据）」；需实测项不得写成结论。
- **不改码纪律**：评审批任何「顺手修」都算违规；发现的缺陷只登记 + 给批次归属。
- **ADR 触发**：仅当出现**结构性决策**（例如：卡体系分层、闸门数量上限、遗留分档规则）才写 ADR，走既有骨架；无决策则明确写「本批不需要 ADR」。
- **单批交付**：评审 + 拆解一批做完；**改进实施另立批次**，不在本批扩张。

## 六、NFRs（业务视角）

- 报告 **≤80 行**（与 arch 既有产物骨架一致）；问题清单每条 **≤3 行**（结论 + 行段 + 建议归属）。
- 行段引用**准确率 100%**（qa 抽查 ≥5 条；引用不存在或指错行 = 不合格）。
- **零双源**：报告引用既有文件时给指针，不复制规则原文。
- 成本：主审 + 交叉合计**不超过一次会话窗口**（用户口径：不要为评审开长跑）；评审不引入新工具链、不联网。
- 可读性：报告需让「没参与过机制细节的人」看懂每条问题**为什么是问题**（一句话后果）。

## 七、AC（五覆盖）

- **AC1（主路径）** 报告存在、≤80 行、含 4 维度结论（自洽 / 膨胀 / 脱节 / 遗留）。
- **AC2（主路径）** 问题清单每条带 `文件:行段` + P1/P2/P3 分级 + 处置归属（本批改禁止 / 哪批改）。
- **AC3（异常）** 4 维度中任一维度若判定「无问题」，必须写「查了什么 + 命令或行段证据」；**禁止**只写「未发现问题」。
- **AC4（边界）** 行段引用抽查 ≥5 条**逐条可达**（qa 独立核，不采信主审自述）。
- **AC5（负向闭环）** 本批 diff 中 `.agents/` / `bin/` / `tests/` **零改动**（`git diff --numstat main...HEAD` 证明），发现的可执行缺陷全部进清单而未顺手修。
- **AC6（设计一致性）** 三档到期遗留逐条给出处置建议（关闭 / 接受含到期 / 合并 / 转办），条数与台账**对得上**（给计数命令）。
- **AC7（可用性）** 至少 1 条拆解**可直接开工**：含范围、AC 草稿、主责角色、预估批次边界。
- **AC8（门禁）** `check` rc=0（`files=54` 不变）；不要求重跑 `npm test`（无实现改动）；PR 形态合规（可读标题 + 无 `wip` 前缀字面量）。

## 八、上线闭环

- **交付**：`docs/reports/118-mechanism-review.md`（≤80 行报告）+ 同文件内问题清单节 + 拆解节（+ 必要时 `docs/adr/<日期>-<slug>.md`）。
- **验收**：PM 核 AC1–AC8；`qa` 交叉复核两件事（声明 vs 判据落差、行段抽查 ≥5 条），结论写进**评审报告末节**而非另开文件。
- **合并**：PM 验收通过后由 `arch-designer` 在 PR 上 `--squash --subject/--body-file` 执行（PM 不亲自合并、不 push main）。
- **发布**：**不发版**（纯文档，`package.json` 不动）。
- **归档**：PRD 落 `docs/prds/`（已建）· 报告落 `docs/reports/` · 遗留清单随下一批首提交回填台账。
- **收尾**：派生会话回收；拆解出的批次登记进 `docs/tasks-state.md` 待派发队列（标注延后/待排期，不自动派发）。

## 九、变更治理

- **范围变更**：任何扩大（如加入实现修复、加入自动化 lint 落地）须 PM 批准并在本 PRD 追加「变更记录」一节；未留痕视为违规。
- **升级为 P0 的例外**：若评审中发现**安全 / 数据丢失**级问题，主审必须**立刻停下报 PM**，由 PM 决定是否中断评审单独立项；**不得**夹带修复。
- **结论纠偏**：PM 或 qa 若证伪主审的某条结论，主审须在报告内**订正并留痕**（写「订正」而非静默改），同 #121 的 impl 报告订正口径。
- **后续改进批次**：本批产出的拆解**不自动开工**；每条需 PM 排期 + 开工确认卡 + PRD（轻通道视规模）。

## 十、优先级（战略筛子 → MoSCoW → RICE → Kano）

- **战略筛子结论**：**命中**。机制的「可信度」是本项目核心资产——后续每个批次都靠它做闸门；机制自相矛盾会以「每批返工」的形式持续收费（#121 一轮 NO-GO + 二轮 CONDITIONAL 即实例）。
- **MoSCoW**：Must = 4 维度评审 + 分级 + 拆解 + 行段可达（AC1–AC7）；Should = ADR（有结构性决策时）；Could = 自动化 lint 建议（只建议不落地）；Won't = 实现修复 / 门禁重跑 / 功能价值评价。
- **RICE**：Reach **1**（单一维护人，但影响**全部后续批次**）· Impact **3**（高）· Confidence **0.8** · Effort **1.5**（主审 + 交叉 ≈1.5 人日）⇒ **RICE ≈ 1.6**。
- **Kano**：基础型（expected quality）—— 做了不会让人惊喜，不做会持续踩坑；无兴奋点属性，故不追加投入。
- **排序**：用户已定「#121 之后紧接着做」；本批**不抢占**其它已排期项（当前待派发队列仅本批）。
