# PRD：门禁分层提速（快档 ≤2 分钟 · 全量留 PR/发布前）

- 状态：待确认（开工前须用户确认）· Owner：PM
- 更新：2026-11-17
- 指针：Issue [#143](https://github.com/Nathan3303/nao-skills/issues/143) · 上游用户诉求（2026-11-17「测试一次太久，估计半个多小时」）· 现门禁口径 `package.json` scripts + `tests/t4/run.sh` + `AGENTS.md`「全范围门禁口径」
- 优先级：战略筛子通过（开发节奏直接受制）· RICE 见附录（Score 16.0，P1）

## TL;DR（≤5 行）

- **做什么**：`npm test` 保持全量语义不变，另加**快档**入口（默认 ≤2 分钟），只收「不依赖真 pi / 真 herdr server」的静态与契约类断言；全量成为 **PR CI 与发布前**的硬门禁。
- **给谁**：本仓维护者与所有贡献者（每天要跑很多次门禁的人）。
- **成功标准**：快档实测 ≤120s 且能抓到「文档/契约/脚本静态面」的回归；全量 rc=0 与现在逐条等价（一条断言都不减少）；先出 profile（per-case 耗时），白名单以数据为准。
- **不做什么**：不删减任何断言；不做「按改动面自动选用例」；不改全量的判据强度与执行顺序；不动 `test:t4:full`（发布前置）语义。

## 一、问题证据

`npm test` = `test:agents`（2s）+ `test:t4`（34 例）。实测单次 **645–830s**（11–14 分钟，跨 6 轮）；`tests/t4/run.sh` **无 per-case 计时**（`grep SECONDS\|date +%s` 只命中缓存清理）；提交高峰期同一批改动会跑 3–6 轮，单次验证链条可达 40–80 分钟。

5 Whys：为什么验证慢 → 每轮都跑全量 34 例 → 因为只有一个门禁入口 → 因为门禁从「最严格可用」出发设计（`tests/t4` 12 例起）→ 因为当时只有发布场景 → 现在日常开发也要跑同一套，成本错配。

## 二、目标指标

- 北极星：快档冷跑 ≤**120s**（p90，本机基线）。
- 支撑：① profile 报告给出 per-case 耗时 top5 与「真机类 / 静态类」划分；② 全量 rc 与断言数与分层前**逐条等价**（差值必须为 0）；③ 快档在受影响面的漏测可举证（哪类改动它抓不到，逐类列出）。

## 三、范围 / 非范围

- **范围**：`tests/t4/run.sh` 增 per-case 计时（`-t` / `--timings`，不改变默认输出）· profile 报告落 `docs/reports/143-profile.md` · 新增快档入口（形态见 §五）· `AGENTS.md` 门禁口径一行更新 · `tests/README.md` 命令表更新。
- **非范围**：1) 删除/弱化任何既有断言——理由：分档的目的不是少测；2) 「按改动面自动选 `--case`」——理由：漏测风险远大于收益，且判定规则会成为新的不可测面；3) 并行执行用例——理由：多数用例共享 herdr pane/server 与 `/tmp` 夹具，并行化属独立工程（若 profile 显示静态类占大头，可另批做静态并行）；4) 改 `test:t4:full` / `test:t4:full:dual` 语义——理由：它们是发布前置，语义不许动。

## 四、用户场景

- **画像**：本仓维护者，一天内反复改 `.agents/**` 或 `tests/**`，每次改完想快速知道「有没有把契约弄坏」。
- **主路径**：`npm run test:fast` → ≤2 分钟内出 rc → 绿则继续改；提交 PR 后 CI 跑全量；发版前跑 `test:t4:full`（含双后端）。
- **异常**：快档绿但全量红（说明改动落在快档覆盖外）→ 记一次「快档漏检」，作为白名单复核输入；快档红 → 照常修。
- **状态**：不适用（CLI，无 UI）；无「加载/空」态。

## 五、业务规则

- **快档白名单判据（唯一、机械）**：用例**不启动** `pi` 进程、**不启动** herdr server（含 `session-start`/`server`）、**不依赖** `TERM_*` 真实后端可用的，才可入快档；判据以「用例是否真起子进程」为准，写入白名单注释，不靠主观分类。
- **白名单以 profile 为准**：最终集合 = 满足上判据的行，**且** profile 显示其为静态类；若某例耗时 ≥20s 即使静态也需在报告里给出理由才纳入。
- **入口形态**（顺序敏感）：① 新增 `npm run test:fast`；② 其内部调用 `test:agents` + `tests/t4/run.sh --fast`（新增 flag）；③ `npm test` 保持全量不变，一字不改。
- **全量等价性**：分档后 `npm test` 的输出与断言计数与本批前**逐条等价**（禁止顺手改断言）。
- **失败语义**：快档跳过某例时**必须显式列出**「本次跳过 N 例（真机类）」，不许静默跳过（防止把跳当绿）。

## 六、NFRs

- 快档冷跑 ≤120s（本机基线，p90）；`test:agents` 不变（2s）。
- 快档**零网络**（与现门禁一致）；不新增依赖。
- 计时实现不得改变默认输出格式（除 `-t` 外逐字不变）——否则会打破现有 golden 类断言。
- 兼容：`NAO_TEST_TERMINAL=tmux` 与 herdr 两种环境下快档都要能跑；`T4_*` 既有环境变量语义不变。

## 七、AC

- 验证接缝：`tests/t4/run.sh`（新 flag）+ `package.json` scripts + QA 自建探针。QA 已确认：待派发后确认。
- AC1（主路径）：Given 干净树，When `npm run test:fast`，Then rc=0 且实测耗时 ≤120s，并打印被跳过的例数。
- AC2（profile）：Given `tests/t4/run.sh -t`，When 跑全量，Then 输出 per-case 耗时表（每例一行，末尾合计），落 `docs/reports/143-profile.md` 含 top5 与分类结论。
- AC3（等价性）：Given 分层前后的 `npm test`，When 对比断言总数与用例数，Then **差值为 0**（禁止顺手改断言）。
- AC4（白名单正当性）：Given 快档白名单，When 逐个核判据「不启动 pi / 不起 server」，Then 无一例违反；反例：把任一真机类用例塞进快档 ⇒ 用例必须红或显式失败（不得静默跳过）。
- AC5（异常 · 不漏不隐）：Given 快档运行，When 有跳过项，Then 输出「跳过 N 例（真机类）」一行；`-v` 可列出名称。
- AC6（负向闭环）：Given 把某条静态断言改坏（如 `AGENTS.md` 数值与常量不一致），When 跑快档，Then 必红（证明快档不是空跑）。
- AC7（边界 · 双后端）：Given `NAO_TEST_TERMINAL=tmux`，When 跑快档，Then rc=0；herdr 下同样 rc=0。
- AC8（文档一致）：Given 本批改动，When 读 `AGENTS.md` 门禁口径与 `tests/README.md` 命令表，Then 与实现逐字一致（`npm test` = 全量、`npm run test:fast` = 快档、发布前置仍 `test:t4:full`）。

## 八、上线闭环

- 不单独发版（工具链改动，随下次 PATCH/MINOR 记录）。
- 上线后：本仓日常改用快档；PR CI 与发版流程继续用全量（`pages.yml` 与发布前置不变）。
- 回滚：`git revert` 单条提交即回到单门禁（快档只是新增入口，回退不影响全量）。
- 观测：两批之内统计「快档绿 → 全量红」的次数；≥2 次则复核白名单。

## 九、变更治理

- `feat` 全通道；**arch 评审按需**（不新增机制语义、不动就绪面 ⇒ PM 初判不需要 arch；若 RD 发现要改 `run.sh` 契约则升格评审）。
- 文档随任务 PR；`AGENTS.md` 只改一行口径 + 指针。

## 附录：战略筛子 / RICE 结论

- 战略筛子：① 直接作用于开发节奏 ② 不动任何断言判据 ③ 可单条回退 —— 通过。
- RICE：Reach 4（贡献者 + 维护者）/ Impact 3（每次验证省 10+ 分钟）/ Confidence 0.9 / Effort 0.7 人日 → **Score ≈ 16.0 → P1**。
- MoSCoW：Must = 快档入口 + profile + 全量等价 + 显式跳过计数；Should = `-v` 列名单；Could = 静态用例并行；Won't（本批）= 删断言 / 自动选例 / 并行真机用例。
