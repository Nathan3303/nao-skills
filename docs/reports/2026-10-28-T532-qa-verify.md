## 缺陷（严重度 / 最小修法）

- **D1（P3）「零外部进程」措辞与实现不符**：默认路径新增 **2 次 `grep` fork**（settings 匹配 + 摘要行抽取；默认 check 总 execve 243 / `-v` 377，codegraph 二进制 0 次）。AC11 的可测判据（codegraph 调用=0）成立。修法：NFR 措辞改为「零 codegraph 调用」或把两处 grep 改 bash 内建（`while IFS= read -r` / 参数展开，约 10 行）。
- **D2（P3）用例 18 夹具把 `node`/`npm` 一并剥离**：本机 `codegraph` 与 `node` 同目录（mise node bin）+ mise shims 也带 codegraph，`NO_CG_PATH` 剥目录 ⇒ 夹具内 `node` 缺失；因夹具只复制 `.agents/`（无 `package.json`）而未触发 `✗ node 缺失` 的 rc=1。**已实测**：同夹具补上 `package.json` 后 check rc=1 ⇒ 属脆弱点（未来夹具补 `package.json` 会变假 FAIL）。修法：用只含 `node`/`npm` symlink 的目录保底（3 行）。
- **D3（P3）声明检测为子串匹配**：被 `pi config` 过滤（`extensions: []`）或 `!` 排除的条目仍判「✓ 齐备」，与 BR9「已声明（未验证生效）」略有张力。修法：文案补半句「（生效还依赖插件未被过滤/禁用）」；不建议解析对象形字段（成本 > 收益）。
- **D4（P3）下游恒 `warn=1` 与 `pm-operations` 规则叠加**：三仓无索引 ⇒ 每次默认摘要带 `warn=1`，而 `pm-operations.md:15` 规定「warn>0 或失败加 -v」⇒ PM 会恒跑 `-v`（+0.4s + 30 行）。修法（二选一）：codegraph `!` 不计入 `warn=` 计数，或该条改为「warn>0 且非 codegraph 态」。
- **D5（P3）文档级不一致**：PRD BR2 称「6 行契约」但枚举 7 条；AC4 要求 6 卡「逐字口径『代码定位：…』」，实现用角色化标签（**定位** / **影响面/调用链评审** / **验收闭环**），阶梯短语逐字一致。修法：PRD 一句订正即可，代码无需改。
- **D6（观察）AC8 第一 Given 未复跑**：真实会话退出后无残留属上游行为；BR11 禁止在仓内跑 `pi`，在 /tmp 副本跑真实会话会引入 ~300MB sidecar + 孤儿 daemon，性价比低 ⇒ 沿用 2026-10-28 接缝实测证据（`session_shutdown` 删除成立；`pi --help`/`pi list` 残留已被 ignore 覆盖）。
