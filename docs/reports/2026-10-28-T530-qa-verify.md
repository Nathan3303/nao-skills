## 6 D-1 风险评审（判断，不是复述）

**结论：建议回流 RD 改为「不可判定 ⇒ 保守拒」（混合策略）；不必重跑本单红/绿证据。**

- 现状是 fail-open：`pane_hosts_caller` 把「祖先链不可读」与「确定不是祖先」都归为 `return 1`（不是自己），而 `cmd_close` 随后会 `tmux kill-pane -t "$pane"`。安全闸门在输入不可判定时放行，方向错误。
- **实证**（隔离 server，可控）：在目标 pane 内真跑 close，仅把 `ps` 换成恒失败（PATH 首位放 `exit 1` 的假 ps）⇒ 调用者自身 pane **被回收（SELF_KILLED）**；对照（ps 正常）⇒ rc=1 + 「拒绝回收」+ pane 存活。即 RD 报告 §7 所说「只会更少拒绝」在自身 pane 场景就是**自杀风险**，不是纯收益。
- 按 PM 提的混合策略：`不可判定 && pane id == ${TMUX_PANE:-}` ⇒ 拒。它能覆盖上述实证（pane 内 `TMUX_PANE` 必为自身 id），且不触碰红态（红态里 ps 正常，祖先链可判定 ⇒ 走原路径）。
- 一点补强建议：与其只靠 `ps`，可在遍历时直接读 `/proc/<pid>/stat` 的 ppid（无外部依赖），或对「不可判定」再加 tty 交叉校验（`#{pane_tty}` vs 调用者 tty）——后者还能覆盖「调用者被 nohup/双 fork 重新挂到 init 后祖先链断裂」这一残留面（此面混合策略也覆盖不到，因为链本身可判为「不是祖先」）。最小可用收口仍是混合策略，约 5 行。
- 严重度/优先级：一般 / P2（触发需 ps/procfs 不可读 + 在自身 pane 内 close；支持的 Linux 环境罕见）。但 F1「绝不回收调用者自己」是硬不变量（T513-S2/T523/T525 血史），**不建议带着已知 fail-open 发版**。
