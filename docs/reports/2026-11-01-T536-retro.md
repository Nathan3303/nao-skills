# L1 复盘：PM 两次转述 worker 的计数类数字而未自证

- 状态：已收口（防线 `T536-E` 随本批落地）· 更新：2026-11-01 · Owner：PM
- 指针：批次 T535（v0.20.3）/ T536（本批）· 触发条件 = **同类问题第二次**（兼返工 ≥1）

## 一、发生了什么

- **第一次（T535 · 2026-10-31）**：rd 报 `tests/t4/lib.sh` SIGPIPE 假 FAIL 为「**2/20**」；QA 独立复核后订正为「**重负载 2/40 · 空载 0/100**」。我当时采纳 QA 订正（处置正确），但**先按 rd 口径写了台账与草稿**，属「先转述、后订正」。
- **第二次（T535 交付 / 2026-11-01 发现）**：rd 与 QA 均报「`tests/t4` **19/19** 例」，我直接写进 v0.20.3 发布说明、PRD 交付记录、PRD 索引与台账。**实为 18 例** —— `bash tests/t4/run.sh --list` 实测注册 18 项（编号 01–10、12–19；`11` 已于 T529 退役）。两方都把「最大用例编号 19」当成「例数」，我未复核即对外发布。
- **影响**：v0.20.3 发布说明有一处用户可见的计数错误（用例 18→19 应为 17→18）；tag 与 Release 正文已发。已在本批（T536）订正仓库内 notes + PRD + 索引 + 台账，并新增「订正说明」段；GitHub Release 正文随下次发布同步订正（已 push 的 tag 按规则不重打）。

## 二、根因（三层）

1. **直接原因**：验收时我核的是「回执是否表单完整 + 数字是否自洽」，**没有对计数类数字做一次独立计算** —— 而 `19/19` 这种「分子=分母」的写法天然自洽，肉眼无法发现错。
2. **机制缺口**：`checklists/pm.md` 的验收条目要求「回执含全量门禁精确数字」，但**没有要求 PM 自己复算至少一项**；T531 加的「根因类派发须附实测」只覆盖**派发方向**，没覆盖**验收方向**。
3. **更深**：worker 与 QA 都可能沿用一个错误的计数口径（本例两方独立报同一个错值），所以「多方一致」不构成证据 —— 只有**一条命令**能证伪。

## 三、改了哪条机制

- **本批（T536 · 范围增补 E · rd-infra 落地）**：`checklists/pm.md` 交付清单 +1 条 —— **计数类数字必须 PM 自证一条命令**：
  - 用例数：`bash tests/t4/run.sh --list | wc -l`
  - 断言数：`grep -c '\[PASS\]'`（或 run.sh 汇总行的 PASS 数）
  - 文件数：`check` 输出的 `files=` 与 `find "$NAO_SKILLS/.agents" -type f | wc -l`
  - 判据：**回执数字与本机命令输出不一致时，以命令为准**，并当场订正回执/文档。
- **配套**：`tests/t4/run.sh --list` 的口径说明写进 `tests/README.md`（注册项数 = 例数；编号不连续属正常）。
- **不做**：不要求 PM 重跑全部门禁（成本过高），只强制**计数类**这一最易错的子集。

## 四、可验证防线

1. **命令**：`bash tests/t4/run.sh --list | wc -l` → 本仓应为 **18**（T536 交付时口径）。
2. **命令**：`grep -cE '^\s*[0-9]{2}\b'` 同义；若两者不一致 ⇒ 注册表与文件集不同步（真缺陷）。
3. **判据（写进清单）**：发布说明/PRD 里的「用例数」若与命令输出不符 ⇒ 验收不通过、已发布则按「订正说明」段落留痕处理。
4. **回归演练**：本批验收时由 PM 亲自跑一次并把输出记入验收评论（首个实例）。
