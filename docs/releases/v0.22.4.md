# v0.22.4 — 新增角色不再被自己的检查拦住

- 状态：**未上 npm（内容已含在 v0.22.5，本版被直接取代）** · tag 与 Release 已发并保留（不删除已发 tag）· 更新：2026-11-06 · Owner：PM

## 本次更新

**这一版没有面向使用者的功能变化，命令行为与 v0.22.3 完全一致。** 它改的是一道自查用的检查——**如果你往舰队里加一个角色，以前会被它拦下来，而且给的理由是错的**。

具体说：这项检查本来是防「角色清单和角色卡对不上」的。但它把「必须正好 7 个角色」写死在代码里，还顺带把「和清单保持一致」的判断建立在真实清单上。于是你正常加第 8 个角色时，会看到 **4 条红**，其中两条与实际不符（说某个新角色是「没登记的孤儿卡」、说体检本该报警却没报）。现在改成：

- 期望值收在**一个文件**里（`tests/t4/expected-roles.txt`），加/删/改名角色只改这一处；
- 改漏了会**只红 1 条**，并且直接告诉你「请更新这个文件」；
- 那两条误导性的红已经消失（负控和复位不再依赖真实清单状态）。

真正的漂移——清单里删了条目、卡表格里没登记、别名不一致、卡文件缺失、卡内声称的角色名与清单不符——**照样精确点名**，一条都没少。

## ✨ 更好用了

（本版无使用者可见的新能力。）

对你的实际影响：**你下次加角色时，只会看到一条明确指路的提示，而不是四条互相矛盾的失败。** 如果你自己也维护角色的清单与卡，这个「期望单文件 + 漏改即指路」的形态可以直接借用。

## ⚠️ 请留意

- **命令与输出没有变化**：`ensure` / `status` / `close` / `check` 与 v0.22.3 一致。
- **有一处刻意的「双写」**：角色的期望值同时存在于 `.agents/roles.yaml`（机制用）和 `tests/t4/expected-roles.txt`（检查用）。这是**有意**的——若让检查从清单自己推导期望，等于用被检对象给自己判分，那道闸就废了。代价是加角色要改两处，收益是漏改必被抓。
- **一个尚未修复的偶发失败**：某个验证会话归属的用例在机器负载高时会偶发红（今天撞了 5 次，每次重跑即绿）。**已知，未在本版处理，下一版专门治**。
