# v0.22.6 — 派单说清楚，比事后返工便宜

- 状态：已核验（npm 已发布：`dist-tags.latest` = 0.22.6 · `dist.integrity` 与本地 tarball 172,118 B 逐字节一致；QA main 复核 GO）· 更新：2026-11-09 · Owner：PM

## 本次更新

**这一版没有面向使用者的功能变化，命令行为与 v0.22.5 完全一致，也没有改动任何脚本或测试。** 它改的是**我们内部怎么派活**——而这恰好是过去几天反复返工的真正原因。

三天里出现 5 次返工，**没有一次是实现写错了**，全是派单时没说清：数据从哪到哪、失败的那几种情形要不要覆盖、断言到哪一层算数。于是每次都是实现按字面做对、复核时才发现洞，然后返工一轮。这一版把三条纪律写成了**可以逐条打勾的清单**（派单前 PM 勾、交付前实现者勾、复核时 QA 勾）：

- **数据通道**：让 A 拿到 B 的数据，必须走文件 / 参数 / 返回值，**不许靠全局变量**（曾经因为这条，一个「无法验证」的情形被误判成「失败」，而且只在网络不通时才发作）；
- **各态断言**：成功 / 失败有输出 / 失败无输出 / 无凭据 / 超时，**五种情形各要一条断言**，且结果只能是「跳过」或「通过」，不许变成「失败」（曾经的教训：全部绿 ≠ 安全，异常路径才是洞的藏身处）；
- **作用域 + 变异自证**：断言必须写明作用在**哪一段文本 / 哪一行 / 哪个字段**，并且要交一份「把这段改空或改错，断言必须红」的证据（曾经两次出现「说明写着收紧了、实际还是整段匹配」）。

另外立了三件运维规矩：**网络出问题时怎么降级**（重试一次 → 如实记录降级 → 逐条标出哪些结论没在线核过，**不许给一个笼统的「通过」**）、**提交说明里怎么提及工作期前缀**（写成「`wip` 前缀（不带左括号）」，否则判据会自己被自己触发）、**新增检查器必须输出稳定顺序**（按「文件:行号」排序，不依赖遍历顺序）。

## ⚠️ 请留意

- **命令与输出没有变化**：`ensure` / `status` / `close` / `check` 与 v0.22.5 一致。
- **这三条纪律目前是「人工可勾选」，不是自动检查**。把它做成脚本只能验「字段写没写」，验不了「选得对不对」——那种检查最后会变成新的形式主义，所以刻意没做。已登记为后续候选，不夹带。
- **网络降级时的「旁证」只用于说明，不构成成败判据**：实测出现过「旁证命令超时、但操作其实成功」的情况，别拿旁证当结论。
