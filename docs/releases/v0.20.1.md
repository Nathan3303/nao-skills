# v0.20.1 — 一个任务一条 PR：文档和台账跟着需求走

- 状态：已发布（v0.20.1 · tag + Release 已发；npm 重发已核验）· 更新：2026-10-30 · Owner：PM

## 本次更新

从这一版起，**一个需求在主干上只留一条提交，而且这条提交包含它的全部改动——代码、测试、文档、任务台账都在里面**。以前文档类改动会单独落一条提交，甚至可能另开一个 PR，结果一个需求散成好几条：想整条回滚要挑好几下，评审时也看不见文档到底改了什么。现在改成：文档与台账在需求分支上提交，随**同一条 PR**合并进主干。

## ✨ 更好用了

- **评审时能看见文档**：PR 的改动清单里就包含需求文档、验收报告和任务台账，不用再另外找「文档 PR」逐条核对。
- **回滚是一个动作**：要撤掉某个需求，撤那一条提交即可，代码与文档一起回退，不会出现「代码撤了、文档还留着」。
- **历史能当目录看**：主干提交列表现在等于需求列表，每条都读得懂在做什么。
- **台账不再落后于代码**：同一个提交里就是同一时刻的事实，接手的人读到的状态与代码同版本。

## ⚠️ 请留意

- **文档 / 台账不再单独提 PR**：需求进行期间产生的文档改动，一律提交在需求分支、随该需求的 PR 合并。唯一例外是「为建立需求单所需的最小摘要」可以单独一条提交（且只含该文件）。
- **需求合并之后才产生的记录**（安装包校验结果、发版说明终态、角色卡广播登记等）**随发版提交一次带走**；发版之后才出现的事实，记进下一个需求的 PR 或下一次发版提交，不再单独落主干。
- **历史不追溯**：本版之前已经单独落在主干上的文档提交保持原样，不改写历史。
- **团队用法不变**：分支、提交前缀、路径级暂存、合并前验收等既有习惯照旧，变的只是「文档跟谁一起走」。
