为什么需要

一个人对着 AI 写代码，常见三个毛病

不是模型不够强，是缺分工与交付纪律。

  • 01

    一个会话什么都干，聊到后面就糊涂了

    拆成 7 个专业角色，各管一段，互不干扰。

  • 02

    需求没问清楚就开写，写完发现不对

    PM 先追问、写清 PRD 和目标，你点头才开工。

  • 03

    干完不知道算不算干完

    每个任务必须回执并按清单自查，PM 逐条验收才归档。

分工

七个角色，各管一段

不想要哪个角色，删掉对应文件即可；只留 PM + 一个研发角色也能跑。

  • 产品经理 pm

    拆需求、写 PRD、派活、验收，唯一的调度者

  • 架构师 arch-designer

    技术选型与方案评审，出 ADR，评影响面

  • UI/UX 设计师 uiux-designer

    信息架构、交互流程、视觉令牌与断点

  • 前端研发 rd-fe

    实现界面与交互，自测通过后回执

  • 后端研发 rd-be

    实现服务与数据，自测通过后回执

  • 测试工程师 qa

    按验收标准出用例、跑门禁、报缺陷

  • 工程基座 rd-infra

    CI、发布、脚本守卫与仓库治理

三步装好

从零到能派活，只要三步

  1. 01

    装前置

    pi ≥1.4.0、终端后端（herdr 默认 / tmux 回退）、Node ≥18、git 都齐了才装得起来。一条命令自检：

    pi --version && node -v && git --version && (herdr --version || tmux -V)

  2. 02

    把机制装进你的项目

    项目级安装：pin 写进 .pi/settings.json 进仓库，团队 clone 即得同款。

    cd 你的项目 pi install --local npm:@nathan33/nao-skill npx @nathan33/nao-skill init

  3. 03

    装协作插件，拉队开工

    插件负责多会话派活；体检 exit 0 就能拉动 7 个常驻会话。

    npx @nathan33/nao-skill plugins install-all .agents/scripts/nao-fleet.sh check .agents/scripts/nao-fleet.sh ensure pm arch rd-fe rd-be qa rd-infra uiux

常见问题

装之前你大概会问这几句

会改我的代码库吗？

只会新增项目根 AGENTS.md、.pi/settings.json，以及一个转发入口 .agents/scripts/nao-fleet.sh。角色卡、清单、技能这些机制文件都在依赖包里，不铺进你的仓库，也不碰你原有文件（已有 AGENTS.md 时是合并追加，不覆盖）。

除了 pi，能配别的编程 Agent 吗？

不能。nao 的多会话派活、回执、回收整套机制都建立在 pi 之上，只支持 pi，不为其他编程 Agent 做适配，也不承诺可互换。

它会在 GitHub 上开 PR 吗？

会。每个需求一条分支、一个 PR（草案早开、CI 早跑），你确认验收后由研发角色 squash 合并，main 上只留 1 条可读提交。没有远端或 gh 时降级为本地分支，流程不变。

跑完的会话要留着吗？

派生会话验收完就回收，常驻角色留着复用。nao-fleet.sh status 会提示哪些是残留，目标在别的项目里也能回收。

为什么需要终端后端？

舰队要把 7 个角色会话放进终端里，还要能可靠地找回与收掉。默认 herdr：每个角色一个 tab，身份靠结构化事实判定；tmux 是回退方案，在当前窗口分屏，SSH 下同样可用。
